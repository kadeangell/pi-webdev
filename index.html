Pi WebDev

An orchestration system for LLM-driven web development. A custom browser, a unified protocol that goes beyond CDP, and tight integration with the Pi coding agent — so an LLM can iterate on a web project at the speed of the dev server, not the speed of Playwright.

This started as a plan and is now built. All eight weeks of the roadmap are in: six subsystems (Lightpanda browser, file watcher, TypeScript LSP, Vite, Vitest, ESLint), 34 WDP methods, React component introspection, a per-turn event digest, and a pi-webdev CLI with init and a daemon installer — 37 end-to-end smoke assertions, all green. See Current state for the full inventory, Progress for the build trail, and the future roadmap for what's beyond 0.1.

The core thesis is that LLM-driven web development is currently bottlenecked by browser tooling that was designed for human QA engineers, not autonomous agents. Playwright + headless Chrome eats 2-5 seconds per iteration. Tight LLM loops need sub-100ms. A purpose-built browser plus a richer protocol that surfaces build state, type errors, dev-server events, and framework-level introspection — wrapped behind a Pi extension — could change what an agent can do in a working session.

02Honest status

The bets the plan made have now mostly been settled by building. Worth being explicit about how they landed:

Confirmed by the build: the orchestration-server / protocol layer was indeed well-understood — handshake-to-ping RTT is ~0.5ms. Lightpanda's CDP is enough to back all five browser methods plus console capture. React's component tree is walkable from a ~150-line in-page script — no react-devtools-core needed. tsserver, Vitest, and ESLint all integrate cleanly via their existing protocols / Node APIs.

Still open after 0.1:

  • Lightpanda's no-layout model and one-target-per-process limit are real constraints — fine for "read and reason," wrong for screenshots / coordinates. A Chromium escape hatch is on the 1.0 roadmap.
  • The Pi extension still binds a stub host; the real defineExtension integration is 0.2's top priority.
  • The digest format works but is a first draft — it needs tuning against real session token-cost data.
  • How much of the protocol survives first contact with real users.

These are tracked honestly in Current state §10.6 and sequenced in the future roadmap.
