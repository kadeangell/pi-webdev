Section 03 · The WDP protocol

The WDP protocol

A JSON message protocol over WebSocket. Bidirectional, streaming, typed. Inspired by CDP and LSP, but with a tighter scope and a token-aware payload design — every message considers what an LLM has to read.

3.1Wire format

WebSocket transport with JSON message framing. Three message kinds:

// Command — client → server
{
  "id": 1,
  "method": "browser.navigate",
  "params": { "sessionId": "abc", "url": "http://localhost:3000" }
}

// Response — server → client
{
  "id": 1,
  "result": { "loaderId": "5C9A...", "frameId": "..." }
}

// Event — server → client, no id
{
  "method": "build.completed",
  "params": { "buildId": "b_42", "duration_ms": 184, "errors": [] }
}

If you're thinking "that's just CDP with different method names" — yes, that's the point. CDP's wire format is well-thought-out; we steal the pattern wholesale. The difference is in the method surface and the event semantics, not the bytes.

Why WebSocket, not stdio

Pi's RPC mode is stdio-based, but the Pi extension speaks WDP over WebSocket to the orchestration server. Reasons:

  • Long-lived server. The orchestration server outlives Pi sessions. WebSocket lets multiple clients attach.
  • Backpressure. WebSocket has well-defined flow control. Stdio doesn't, and a flood of events can deadlock.
  • Multi-tenant. Eventually you'll want one server, multiple projects. WebSocket session IDs are the natural disambiguator.
  • Observability. WebSocket traffic is trivial to inspect via DevTools or a TUI dashboard.

3.2Tool surface

Methods are grouped by domain, with names borrowed from CDP convention where applicable. The full v0 surface — about 35 methods:

Domain: session

session.create(opts)              → { sessionId }
session.list()                    → { sessions: [...] }
session.close({ sessionId })      → { closed: boolean }
session.capabilities()            → { browser, lsp, frameworks, ... }

Domain: files

files.read({ path, range? })            → { content, encoding }
files.write({ path, content })           → { written, build_invalidated }
files.list({ glob })                     → { paths: [...] }
files.depGraph({ entry })                → { graph: { nodes, edges } }
files.watch({ pattern, since? })         → events stream

Domain: browser

browser.navigate({ sessionId, url })             → { loaderId }
browser.dom({ sessionId, selector?, mode })      → { tree | text | aria }
browser.eval({ sessionId, expression })          → { result, exception? }
browser.click({ sessionId, selector })           → { dispatched }
browser.fill({ sessionId, selector, value })     → { dispatched }
browser.console({ sessionId, since? })           → { messages: [...] }
browser.network({ sessionId, since? })           → { requests: [...] }
browser.screenshot({ sessionId, reason })        → { png_b64 }

Domain: build

build.status()                          → { state, errors, warnings, buildId }
build.errors({ since? })                → { errors: [...] }
build.trigger({ files? })               → { buildId }

Domain: types

types.diagnostics({ scope?, since? })   → { diagnostics: [...] }
types.hoverInfo({ file, line, col })    → { contents, range }
types.definition({ file, line, col })   → { locations: [...] }
types.references({ file, line, col })   → { locations: [...] }

Domain: test

test.list({ pattern? })                 → { tests: [...] }
test.run({ pattern?, watch? })          → events + { results }
test.coverage({ scope? })               → { coverage }

Domain: lint

lint.diagnostics({ scope?, since? })    → { diagnostics: [...] }
lint.fix({ scope? })                    → { fixed: [...], unfixed: [...] }

Domain: inspect (framework-specific)

inspect.componentTree({ sessionId })            → { tree }
inspect.componentByQuery({ sessionId, query })  → { matches }
inspect.props({ sessionId, componentId })       → { props }
inspect.state({ sessionId, componentId })       → { state, hooks }

Domain: env

env.digestSinceLastTurn({ sinceTimestamp })     → { events, summary }
env.detectFramework()                            → { framework, version, config }
env.routes()                                     → { routes: [...] }

The exact method names, parameter shapes, and which events get rolled up into the digest are all things I expect to revise heavily once the first version is in real use. The surface above is the right shape but the details will change. Don't carve any of this in stone before week 4 of the roadmap.

3.3Event surface

Events fire whenever subsystem state changes. The orchestration server buffers and digests them, but a client can also subscribe to the raw stream for debugging:

// File events
files.changed       { path, kind: "modify" | "create" | "delete" }
files.dep_changed   { from, to, kind }

// Build events
build.started       { buildId, trigger }
build.completed     { buildId, duration_ms, errors, warnings }
build.failed        { buildId, error }

// Type-system events
types.diagnostics_changed   { added, removed, modified }

// Dev server events
hmr.update          { modules, accepted }
hmr.reload          { reason }

// Browser events
browser.console     { sessionId, level, text }
browser.navigated   { sessionId, url, frameId }
browser.network_failed   { sessionId, url, status }

// Test events
test.started        { runId, pattern }
test.result         { runId, name, status, duration_ms, error? }
test.completed      { runId, passed, failed, total }

// Lint events
lint.diagnostics_changed   { added, removed }

// Framework events
inspect.tree_changed   { sessionId, changedNodes }

3.4The digest

Events stream into the orchestration server continuously, but the LLM only sees them at turn boundaries, in a compact digest. The digest format is the highest-leverage piece of token engineering in this protocol:

// What the LLM sees, injected as a system message
ENVIRONMENT EVENTS since last turn (2.3s):
  build: ✓ ok (184ms)
  types: 2 errors added, 1 fixed
    src/components/Button.tsx:42 — Type 'string' not assignable to 'number'
    src/pages/api/user.ts:18 — Property 'email' does not exist on 'User'
    [fixed] src/utils/date.ts:7 — Argument of type 'unknown'...
  hmr: 3 updates (Button.tsx, useUser.ts, theme.css)
  browser-1: 1 console.error
    [error] Uncaught TypeError: Cannot read property 'map' of undefined
       at UserList (UserList.tsx:34:12)
  tests: 1 changed (UserList.test.tsx — was passing, now failing)

Design principles for the digest:

  • Token-bounded. Default budget ~500 tokens. If events exceed it, summarize aggressively and let the LLM ask for detail.
  • Recency-weighted. Events relevant to recently-edited files come first.
  • Inline summaries before lists. The LLM should know "2 type errors added" before it reads them.
  • Status icons that read at a glance. ✓, ✗, ~ are denser than "ok / failed / changed".

I don't know what the right token budget is. 500 feels about right for typical sessions, but a complex refactor that touches 30 files might genuinely need a richer digest, and a trivial single-file edit needs much less. Probably we want a configurable budget that auto-tunes based on recent context pressure. Worth measuring.

3.5Capability negotiation

Not every project has TypeScript. Not every dev server supports HMR. The orchestration server's session.capabilities() response advertises what's available, and Pi's extension only registers tools the server supports:

{
  "browser": {
    "engine": "lightpanda",
    "version": "0.4.2",
    "features": ["dom", "js", "fetch", "cookies"],
    "limitations": ["no-webrtc", "no-webgl", "no-service-workers"]
  },
  "lsp": {
    "typescript": { "version": "5.9.0" },
    "available": ["typescript", "eslint"],
    "not_detected": ["rust-analyzer", "pyright"]
  },
  "devServer": {
    "type": "vite",
    "version": "7.1.0",
    "hmr": true,
    "routes_endpoint": false
  },
  "framework": {
    "detected": "react",
    "version": "19.1.0",
    "introspection": "react-devtools-backend"
  },
  "test": {
    "runner": "vitest",
    "version": "3.0.0"
  }
}

Tools that depend on un-detected capabilities don't get registered with Pi. The LLM never sees inspect.componentTree in a Vue project that uses React DevTools terminology.

The handshake and error-code sections below are now implemented — see Progress §0.4. The shape held; the only adjustment was nailing down specific codes (-32001 HandshakeRequired, -32002 UnsupportedProtocolVersion, -32003 AlreadyInitialized) in the JSON-RPC server-defined range.

3.6Versioning

The protocol is versioned at the connection handshake. Clients send their supported version range; the server picks the highest mutually-supported version.

// Handshake (first message client → server)
{ "method": "$/initialize",
  "params": { "client": "pi-webdev-extension", "supportedVersions": ["0.x"] }}

// Server response
{ "result": { "version": "0.1.2", "capabilities": {...} }}

Within 0.x, breaking changes are documented in a CHANGELOG with explicit migration notes. At 1.0, we commit to backward compat within major versions.

3.7Error semantics

Errors come in three flavors with different recovery behavior:

KindCode rangeRecovery
Protocol errors-32xxxClient bug; should not retry
Tool errors1xxxUser/environment error; LLM should adapt
Transient errors2xxxServer should retry with backoff

Critically — tool errors return enough structured context for the LLM to recover without re-asking. A type error response includes the file path, the line, the diagnostic, AND the suggested action. The agent shouldn't have to make three round-trips to get all the info it needs to fix a problem.

3.8Backpressure

Event volume can be high — a webpack rebuild can emit hundreds of events in a second. We need to not flood:

Event coalescing. Within a 100ms window, similar events are merged. Ten files.changed events for ten files become one event with ten paths.

Subscription filtering. Clients explicitly subscribe to event categories. Pi's extension subscribes to high-level events (build status, type errors, browser console); raw event streams are opt-in for debugging tools.

Digest buffering. Events stream into a per-session ring buffer; the digest reads from the buffer at turn boundaries. Out-of-order or replay-after-disconnect is supported via event sequence numbers.

3.9What WDP is not

A few non-goals worth being explicit about:

Not a replacement for LSP. The orchestration server runs an LSP internally and re-exposes a subset of its capabilities. Direct LSP clients (Neovim, VSCode) talk to tsserver directly, not through WDP.

Not a build system. We adapt to whatever build tool exists (Vite, webpack, etc.). We don't ship a build tool.

Not a CI tool. The protocol works fine in CI (run Pi non-interactively, get a digest), but it's not a Jenkins / GitHub Actions integration. That's a layer above.

Not internet-accessible. WDP is local-only by design. A future "cloud orchestration" might exist, but it'd be a different protocol with different security assumptions.
