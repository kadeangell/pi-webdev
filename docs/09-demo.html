Demo

A live walkthrough of the foundation against a fixture React project — examples/counter-app/. Every transcript on this page is real output captured from the pi-webdev CLI on this branch. Nothing here is staged or mocked.

9.1The fixture

A tiny Vite + React 19 + TypeScript + Vitest project. It exists for one reason: to give the orchestration server something to detect.

examples/counter-app/
├── package.json         react 19, vite 7, vitest 3, typescript 5
├── tsconfig.json
├── index.html
└── src/
    ├── main.tsx
    └── Counter.tsx      a one-button counter component

9.2The CLI

A new @pi-webdev/cli package ships a pi-webdev binary. It speaks WDP to a running orchestration server, or — with --auto — boots one in-process for the duration of a single command. Useful for scripts, demos, and one-shot queries.

$ pi-webdev --help pi-webdev — orchestration server client + helpers USAGE pi-webdev [--url URL | --auto] [--project-root DIR] [--json] <command> [args] COMMANDS ping [--echo TEXT] Round-trip a $/ping. Reports RTT. caps Print server capability snapshot. subsystems List subsystems and states. methods List all registered WDP methods. files list [GLOB] [--limit N] List project files (default skip rules apply). files read PATH Read a file and print its content. files write PATH Write a file. Content read from stdin. serve Run the orchestration server (no client). FLAGS --url URL WDP endpoint. Default ws://127.0.0.1:48710/wdp. --auto Boot an ephemeral server in-process and connect. --project-root DIR Project root for --auto. Default cwd. --json Print machine-readable JSON instead of formatted text.

9.3Round-trip

The bottom of the stack — $/ping through the full transport. Boot the server, handshake, ping, tear down, all under a second.

$ pi-webdev --auto --project-root examples/counter-app ping --echo demo-ready pong rtt=0.76ms echo="demo-ready"

Sub-millisecond round-trip on localhost — handshake amortised, transport overhead is essentially nothing. The eventual ceiling is the LLM's tool-call latency, not WDP.

9.4What the server detects

The orchestration server reads examples/counter-app/package.json at startup and emits a capability snapshot. session.capabilities re-exposes it any time.

$ pi-webdev --auto --project-root examples/counter-app --json caps { "methods": [ "$/initialize", "$/ping", "files.list", "files.read", "files.write", "session.capabilities", "session.subsystems" ], "browser": { "engine": "none", "features": [], "limitations": ["browser-subsystem-not-implemented"] }, "lsp": { "available": ["typescript"], "not_detected": ["eslint"], "typescript": { "version": "^5.6.0" } }, "devServer": { "type": "vite", "version": "^7.1.0", "hmr": true }, "framework": { "detected": "react", "version": "^19.1.0", "introspection": "react-devtools-backend" }, "test": { "runner": "vitest", "version": "^3.0.0" }, "projectRoot": "examples/counter-app" }

What the LLM gets from one handshake call: it's a React 19 project, dev server is Vite 7 with HMR, type-checker is TypeScript 5.6, tests run on Vitest 3, and seven WDP methods are dispatchable this session. No probing required.

The browser.engine: "none" is honest — we haven't built the browser subsystem yet, and the capability surface says so explicitly rather than pretending. That's a deliberate choice from doc 03 §3.5: capability negotiation should advertise the truth.

9.5Subsystems

Live state of every subsystem the orchestration server is supervising. Today there's one — files — running in-process.

$ pi-webdev --auto --project-root examples/counter-app subsystems files ready

When the browser subsystem lands in week 2 of the roadmap, it'll appear here too, in starting → ready → maybe crashed → ready if Lightpanda is having a moment. State transitions also broadcast as $/subsystem.status events so the digest can surface them at turn boundaries.

9.6Listing files

Default ignore list (matching common Node project skip rules) keeps the listing pertinent — no node_modules, no .git, no dist.

$ pi-webdev --auto --project-root examples/counter-app files list index.html package.json src/Counter.tsx src/main.tsx tsconfig.json $ pi-webdev --auto --project-root examples/counter-app files list "**/*.tsx" src/Counter.tsx src/main.tsx

9.7Reading a file

$ pi-webdev --auto --project-root examples/counter-app files read src/Counter.tsx import { useState } from "react"; export function Counter() { const [count, setCount] = useState(0); return ( <button onClick={() => setCount((c) => c + 1)}> count: {count} </button> ); } [209 bytes]

1 MiB cap per call; pass range to walk larger files. Path traversal outside --project-root returns 10200 InvalidArgument rather than reading anything.

9.8The smoke test

pnpm smoke is the live spec — fourteen assertions covering the round-trip, error semantics, subsystem state, and the read/write/list surface. This is what we run before every commit on the foundation.

9.9What this proves

Three things, concretely:

  1. The protocol works end-to-end. Handshake, capability negotiation, command dispatch, per-connection error semantics, and event broadcasting are all real. The wire format from doc 03 survives implementation.
  2. Capability detection is useful immediately. Static package.json introspection is enough to give an LLM a complete picture of the project's tech stack in one round trip. No subsystem spawning, no warmup time.
  3. Subsystems compose cleanly. The files subsystem is in-process, registers four lines on the dispatcher, and contributes a files state row to session.subsystems without any registry changes. The next subsystem (likely browser, in-subprocess) will plug into the same shape.

What this doesn't prove yet, and what comes next: the browser subsystem, the dev-server adapter, the LSP, the digest. Those are weeks 2–6 of the roadmap. The foundation that makes them all fit is what's running on this page.
