Section 07 · Roadmap

Roadmap

An eight-week MVP, in four phases. Each phase has one demo-able outcome and one go/no-go decision at the end. The intent is to validate the hardest assumptions early — the lightweight browser and framework introspection — and defer the polish work.

7.0Phase 0 — Spike (week 0)

One week before the formal plan kicks off. Goal: prove the smallest meaningful loop end-to-end with the worst code you can stand to write.

Deliverable

A 200-line Pi extension that exposes three tools (browser.navigate, browser.dom, browser.eval) against stock Lightpanda. Run Pi against your latest React project. Ask Claude (via Pi) to fix a bug. Watch where the friction is.

Why this matters

The spike is the document that tells you what the protocol should actually look like, built from real friction rather than from a whiteboard. Everything in the formal plan below should be revisited after this week.

Go/no-go

If after one week the LLM can fix a one-line bug in a React project, even slowly, you have signal that the architecture works. If Lightpanda crashes on the test project or can't load Vite's HMR client, that's an early indicator to revisit section 04 before committing further.

7.1Phase 1 — Foundation (weeks 1–2)

Goal: ship a working orchestration server with the browser subsystem and a minimal Pi extension, end-to-end.

Week 1 — Skeleton · done

  • Repo setup. Monorepo (pnpm workspaces): packages/server, packages/pi-extension, packages/shared-types
  • WDP wire format and basic transport (WebSocket, JSON framing)
  • Capability negotiation handshake
  • Subsystem supervision skeleton (spawn, heartbeat, restart) — lifecycle + heartbeat in; restart-with-backoff deferred until we have a real subsystem to tune against
  • Pi extension registers a single tool ($/ping) that round-trips through WDP

Week 1 landed. See Progress §0.2 for what shipped and §0.3 for what was learned. Measured handshake-then-ping RTT on localhost: ~0.5ms, ~100× under the protocol's read-op target.

Week 2 — Browser subsystem · done

  • Integrate Lightpanda as a child process — subprocess lifecycle owned by SubsystemRegistry; binary auto-resolved from PATH or LIGHTPANDA_BIN; gracefully absent when not installed.
  • Implement browser.navigate, browser.dom, browser.eval, browser.click, browser.fill — landed.
  • Semantic-tree extraction (no layout; just text, ARIA, visibility, form state) — text + html + aria modes; ARIA falls back to text when Lightpanda's a11y tree is empty.
  • Console event streaming — landed (browser.console, ring-buffered 500 entries per session). Network events deferred until they're needed.
  • End-to-end: LLM can navigate to a URL and read the page — proven by the smoke test and demo §9.8.

Week 2 landed against the real Lightpanda binary (1.0.0-nightly). See Progress §0.7 for what shipped and what we learned about CDP-the-protocol-vs-Lightpanda-the-implementation. Smoke test grows to 23 assertions, including the full browser flow (create session → navigate → eval → click + verify → fill + verify → console replay → close).

Demo at end of phase 1

Pi session: "Tell me what's on the homepage of localhost:3000." LLM uses browser.navigate and browser.dom, returns a summary. Total time from pi start to answer: <3s.

Go/no-go

If Lightpanda can't reliably render your target React projects, swap to the Plan B (Playwright + Chromium pool, slower but works). Don't continue with the rest of the plan on a foundation that's broken.

7.2Phase 2 — Dev loop (weeks 3–4)

Goal: wire in the file watcher, dev server adapter, and the per-turn digest. This is the phase that delivers the "agent feels the dev loop" magic.

Week 3 — File watcher + Vite adapter · done

  • File watcher using chokidar; project index with ignore rules — landed. Events coalesce within a 100ms window and broadcast as WDP files.changed; ring-buffered 1000 events for files.changedSince digest queries.
  • Dependency graph for TypeScript/JavaScript (esbuild-based scanner) — landed via files.depGraph. Externals are marked rather than resolved, so node_modules show up as edge endpoints without being scanned.
  • Vite adapter — registered as the vite subsystem. Connects via build.connect({url}) over the HMR WebSocket (subprotocol vite-hmr); auto-probe optional. Stays in disconnected state when no Vite is running.
  • WDP files.* (read, list, write, changedSince, depGraph) and build.* (status, connect, disconnect) methods — registered.
  • HMR ↔ browser bridge: when the adapter receives a non-accepted update or full-reload, the server triggers location.reload() in every open browser session.

Week 3 landed. See Progress §0.9 for what shipped and what was learned. Smoke test grows to 27 assertions; methods registered: 21 (up from 16). Vite connection is exercised manually rather than in the smoke run — running a full Vite dev server inside the smoke harness would balloon test time without proving anything the unit-level reconciliation doesn't already prove.

Week 4 — Digest + per-turn injection · done

  • Event coalescing and buffering — landed at the orchestration server's broadcast() hot path; every event is recorded in a 2000-entry ring buffer that backs the digest.
  • Digest formatter — token-bounded (chars/4 estimate), per-domain summary rows, status icons (✓ ✗), recency-weighted, raw events trimmed to fit. env.digestSinceLastTurn({ since?, budgetTokens? }) + env.detectFramework registered.
  • Pi extension's onTurnStart hook calls the digest and appends as a system message when non-empty. Failure is silent — never block a turn.
  • Per-connection cursor management: digest returns a cursor ISO timestamp; subsequent calls without since auto-advance from the last cursor. Cursors are forgotten on disconnect.

Week 4 landed. Tuning lives in Progress §0.11; the digest format is still subject to revision once we run real Pi sessions against it. Smoke test now 29 assertions.

Demo at end of phase 2

Pi session: "Add a button to the homepage that increments a counter." LLM edits the file, sees the HMR event in the next turn's digest, queries the DOM to verify, fixes any type errors that appeared. Total iteration: 2-3 turns instead of 6-8.

Go/no-go

If the digest is consistently making things worse (over-injecting noise, distracting the agent from the user's question), redesign the digest format before adding more subsystems. Don't pile on; fix the foundation first.

7.3Phase 3 — Types and tests (weeks 5–6)

Goal: hook in the LSP and test runner. The agent stops needing to "run npm test" and parse stdout; it gets structured signals.

Week 5 — TypeScript LSP

  • Spawn and manage tsserver as a child process
  • Project boundary detection (one tsserver per tsconfig)
  • Implement types.diagnostics, types.hoverInfo, types.definition, types.references
  • Diagnostic events stream into the digest with added, removed, modified deltas
  • Add types.diagnostics to the Pi tool surface

Week 6 — Test and lint

  • Vitest integration via programmatic API
  • ESLint integration via Node API
  • Affected-tests-only optimization using the dep graph from week 3
  • Test events into the digest; lint diagnostics into the digest
  • Implement test.run and lint.diagnostics tools

Demo at end of phase 3

Pi session: "The UserList test is failing — fix it." LLM sees the test failure in the initial digest (no need to run tests manually), reads the test, reads the component, makes a fix, sees the test pass in the next digest. Done in 3-4 turns.

Go/no-go

If tsserver integration is flaky (false positives, slow startup, memory leaks), consider falling back to a simpler tsc --watch spawn-and-parse-stdout approach. Real tsserver is better when it works but isn't worth weeks of pain.

7.4Phase 4 — Framework introspection + first release (weeks 7–8)

Goal: ship React component introspection — the differentiating feature — and make a public 0.1 release.

Week 7 — React DevTools backend integration

  • Inject react-devtools-core backend into the page on browser subsystem startup
  • WebSocket bridge between the in-page backend and the orchestration server
  • Implement inspect.componentTree, inspect.props, inspect.state
  • Stable component ID synthesis (path + name + key hash)
  • Indexed hook value extraction (no source-map analysis yet)

Week 8 — Polish and release

  • pi-webdev init command, daemon installer
  • Docs site (this site, made public)
  • Three high-quality demo videos: "fix a React bug", "add a feature with HMR", "debug a failing test"
  • npm publish: @pi-webdev/server and @pi-webdev/coding-agent
  • Public 0.1 release

Demo at end of phase 4

Public, with a short showreel demonstrating each subsystem doing its part. Open-source the protocol spec and the server. Soft launch on HN, Show HN, relevant Discords.

7.5What's deliberately not in the MVP

Worth being explicit about deferred scope:

  • Vue, Svelte, Solid introspection. React first; others when there's clear demand or contributor energy.
  • Source-map-aware hook naming. Indexed hooks ship in v0; named hooks in 0.2.
  • Next.js dev server adapter. Vite first. Next requires version-specific work; ship after the Vite path is solid.
  • Production-build introspection. Dev-mode only in v0.
  • Time-travel debugging. Tree snapshots per commit are easy to add later; not v0.
  • Multi-project orchestration. One project per server instance for now.
  • Remote orchestration / cloud devcontainers. Local only.
  • MCP server bridge. Sketched, not built. Add when a real MCP customer asks.
  • Visual regression testing. The Chromium escape hatch handles ad-hoc screenshots; full VRT is a separate product.
  • Code generation skills. No /generate-component built-ins — leave that to Pi's existing flexibility.

7.6Beyond MVP — direction without commitment

What 0.2 through 1.0 might look like, ordered by likely value:

  1. Next.js adapter (clears the biggest single-framework gap)
  2. Vue 3 introspection (largest non-React community)
  3. Source-map-aware hook naming (large quality-of-life improvement for React)
  4. Visual correlation: map a screenshot region back to the component that rendered it
  5. Production-build introspection via source maps
  6. Cloud orchestration server for Codespaces, Coder, etc.
  7. Plugin SDK for community-contributed framework adapters

None of these are committed. The MVP usage data will pick the order.

7.7Resource shape

What "ship the MVP" actually takes:

ResourcePhase 0–4 estimate
Engineering (you, full-time)8 weeks
Engineering (one collaborator, part-time)Helpful but not required
Cloud / infra spendNear zero — local-first
Tooling (model API costs for dogfooding)~$50–200/month
Design (this docs site, demo videos)Maybe 1 week of focused work in phase 4

Eight weeks is aggressive but feasible if you stay disciplined about scope. The plan above includes everything needed for a credible 0.1 — no more, no less. Every "wouldn't it be nice if" is in the deferred list above, on purpose.

7.8What to do first (today)

Before any of the above:

  1. Clone Pi locally and read its source. The extension API contract has to live in your head before you write the first line of pi-webdev.
  2. Clone Lightpanda and run it. Open the project you most often work on, try basic operations. Find one site or framework it breaks on, just to calibrate your expectations.
  3. Write the spike (phase 0 deliverable) before week 1 starts. The friction you find there shapes everything downstream.

If after step 2 Lightpanda is clearly not going to work, swap to Plan B (Playwright + Chromium pool) for v0 and revisit lightweight-browser exploration in a separate workstream. Don't let browser choice become a critical-path blocker.
