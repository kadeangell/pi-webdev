Section 05 · Subsystems

Subsystems

Four supporting subsystems beyond the browser: file watcher, TypeScript LSP, dev server adapter, and test/lint runner. Each is replaceable, each speaks a narrow internal protocol to the orchestration server, each contributes to the digest the LLM sees at each turn.

An early version of the files subsystem is now live in packages/server — see Progress §0.2. It implements files.read and files.list (with glob) in-process; the dep graph, write surface, and chokidar-backed watcher arrive in week 3 per roadmap §7.2. Key finding: subsystems don't have to be subprocesses — the registry contract is the same either way.

5.1File watcher

Responsibility: maintain a real-time view of the project's file state and a dependency graph that's queryable without a full re-scan.

Implementation

Use chokidar as the OS-event abstraction. It's the de facto standard, handles platform quirks (macOS FSEvents, Linux inotify, Windows ReadDirectoryChangesW), and integrates cleanly with Node.

Beyond raw FS events, the file watcher maintains:

  • A project index: every file, with size, mtime, hash
  • A dependency graph: which files import which, computed from AST
  • An ignore set: node_modules, .git, build outputs, .gitignore-respecting
  • A "what changed since timestamp X" query API for the digest

Dependency graph

This is the bit that's more work than it looks. Languages vary:

  • TypeScript / JavaScript — parse imports with a fast esbuild-or-swc-based scanner; resolve via tsconfig paths
  • CSS — @import directives, plus PostCSS / SCSS chains
  • Svelte / Vue — multi-language single-file components need component-aware parsing
  • Static asset references — best-effort regex over JS / CSS string literals

For v0, JS/TS only. Other languages return "dep graph unavailable" from the WDP layer. Project-wide changes that touch CSS or Vue components are still detected; we just don't compute the dependency closure for them.

The dependency graph is potentially the most useful thing the file watcher provides to the LLM ("which other files might be affected by this change?"). But it's also the part most likely to be wrong in edge cases — dynamic imports, conditional requires, JSX-driven imports. Worth shipping a clearly-imperfect version early and iterating, rather than waiting for correctness.

WDP surface

files.list({ glob? })             // all files matching glob
files.read({ path, range? })       // file content
files.write({ path, content })     // writes; triggers dep invalidation
files.depGraph({ entry })          // dependency closure from entry
files.changedSince({ timestamp })  // for digest construction

5.2TypeScript LSP

Responsibility: surface TypeScript diagnostics, hover info, definitions, references. Cache aggressively so each LLM query is sub-10ms.

Implementation

Run tsserver (the TypeScript server) as a child process and speak the LSP protocol to it. Don't reinvent — tsserver is the same engine that powers VSCode's TypeScript support, plus every other TypeScript-aware editor.

Process model:

  • One tsserver per tsconfig (most projects have one)
  • Persistent — boots when orchestration server boots, stays warm
  • Project files registered up-front, then incremental on file change
  • Background --watch-style compilation; results stream into the orchestration server

What's exposed via WDP

types.diagnostics({ scope?, since? })
types.hoverInfo({ file, line, col })
types.definition({ file, line, col })
types.references({ file, line, col })
types.completions({ file, line, col, prefix? })  // future

The high-value one is types.diagnostics, especially with since — "what type errors are new or fixed since the last LLM turn?" This is the single signal the LLM needs to know whether its edit broke or fixed something.

What's not exposed

Code actions, refactorings, rename, organize imports. These are useful but redundant — the LLM can do them itself, and exposing them creates a temptation for the model to invoke "auto-fix" tools instead of understanding the problem.

I'm 70% confident on this design choice. The argument the other way: a "fix import" tool that does the obvious thing in 100ms saves the LLM a turn. Worth measuring whether agent quality drops when these are unavailable.

5.3Dev server adapter

Responsibility: hook into the project's dev server (Vite, Next, Remix, Astro, SvelteKit, Vinxi, Rspack) to observe build state and HMR events.

Adapter-per-framework

Each dev server has its own hooks, plugin API, event surface. We ship adapters that all conform to the same internal interface:

interface DevServerAdapter {
  detect(projectRoot: string): Promise<boolean>
  attach(projectRoot: string): Promise<void>

  onBuildStart(handler: (e: BuildStartEvent) => void): void
  onBuildEnd(handler: (e: BuildEndEvent) => void): void
  onHmrUpdate(handler: (e: HmrUpdateEvent) => void): void
  onError(handler: (e: BuildErrorEvent) => void): void

  routes(): Promise<Route[]>
  triggerBuild(opts?: BuildOpts): Promise<BuildId>
}

Adapter implementations

Vite. Plugin API with hooks for buildStart, buildEnd, handleHotUpdate. Easiest case. WebSocket connection to Vite's own server for HMR events. Ship this first.

Next.js. Harder — Next's dev server is more opaque. Two options: (1) a Next plugin that re-exports events; (2) tail the dev server's stdout and parse compilation messages. Plugin route is cleaner if Next exposes the right hooks; stdout-parsing as fallback.

Astro / SvelteKit / Remix. Most of these are Vite-based under the hood. The Vite adapter usually works with minor adjustments.

Other (webpack, Rollup, esbuild standalone). Less critical for v0. Ship a generic "tail logs and regex" adapter as a fallback.

Next.js's internals change between versions and they aren't stable third-party APIs. We might need version-specific adapters (Next 14, Next 15, Turbopack vs webpack). This is meaningful ongoing work, not a one-time write.

The HMR ↔ browser bridge

The single most magical user-visible feature: when the dev server emits an HMR update, the browser subsystem receives it and applies it without a full reload. The LLM sees the change reflected in the next semantic-tree query without paying a navigation cost.

This bridge is just an event subscription from the dev server adapter to the browser subsystem, mediated by the orchestration server. The protocol:

devServer → orchestration: HmrUpdateEvent { modules, accepted }
orchestration → browser.applyHmrUpdate(sessionId, update)
browser → orchestration: applied { duration_ms } | error

If the in-place HMR update fails (e.g., a state-breaking change), the browser does a full reload as fallback. Either way, the LLM sees a single event in the next digest: "HMR applied" or "HMR fallback → reloaded".

5.4Test and lint runner

Two adjacent subsystems, often consolidated into one process. Responsibility: run tests and linters on demand, expose results as structured events.

Test runner integration

Vitest first (Vite-native, fastest, growing share). Jest as a fallback. Playwright for E2E when the LLM explicitly asks.

Run Vitest in its programmatic API, not as a child process. This gives us structured access to test results, not stdout-parsing:

import { startVitest } from "vitest/node";

const vitest = await startVitest("test", [], {
  watch: false,
  reporters: [customReporterThatEmitsWdpEvents]
});

Tests emit per-test events as they complete, so the LLM can react to the first failure without waiting for the whole suite.

Lint runner integration

ESLint via its Node API, same pattern. Run on a file-change trigger; cache results; expose diagnostics through WDP.

Prettier integration optional. The LLM is usually fine reading raw prettier output; we don't need a structured surface for it.

The "what changed" optimization

Running the entire test suite or linting the whole project on every LLM turn would be slow and noisy. We use the dep graph from the file watcher: when the LLM edits UserList.tsx, only run tests that transitively import UserList.tsx, only lint UserList.tsx and adjacent files. The "test ran but didn't change result" events get squelched from the digest.

Mapping "edits to file X" → "tests affected by file X" requires the test files to be in the dep graph, which they usually are but not always (Vitest config can include tests by glob without explicit imports). May need a per-project hint or auto-discovery on first run.

5.5Subsystem supervision

All subsystems are child processes of the orchestration server. The server owns their lifecycle:

  • Spawn: on demand or at startup, depending on detected capabilities
  • Health: heartbeat ping every 5s; missed heartbeat → restart
  • Crash: exit code captured, restart with backoff, emit subsystem.crashed event
  • Resource caps: per-subsystem RAM and CPU limits via cgroups (Linux) or kernel queues (macOS) where available

The Pi extension never sees subsystem state. From its perspective, the orchestration server just always works.

5.6Where subsystems run

By default: locally, in the same machine as the user's project. No reason to be elsewhere.

Future considerations (out of scope for MVP):

  • Remote orchestration server for cloud development environments (Codespaces, Coder)
  • One server per devcontainer
  • Multi-developer shared orchestration for pair-programming sessions

None of these affect the v0 architecture as long as we keep the protocol clean and stateless-where-possible.
