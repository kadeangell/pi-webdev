Progress

A living log of what's been built against the plan, what was learned along the way, and where the plan has shifted as a result. The other docs are the destination; this one is the trail.

0.1Where we are

Phase 1 Weeks 1, 2, and 3 are in. The orchestration server supervises three subsystems (in-process files with chokidar + esbuild dep graph, subprocess Lightpanda, Vite adapter), exposes 21 methods, and broadcasts files.changed / hmr.update / build.completed events for digest construction. An LLM (or the human at the pi-webdev CLI) can navigate a real browser, click and fill, observe console output, query the project's dependency graph, and see file changes stream in as events.

The smoke test (pnpm smoke) now asserts twenty-seven things end-to-end:

  • Handshake completes with a capabilities snapshot.
  • $/ping echo round-trips; bare $/ping also works.
  • Double $/initialize on one connection is rejected (-32003 AlreadyInitialized).
  • Unknown methods return -32601 MethodNotFound.
  • session.subsystems reports the files subsystem in ready state.
  • session.capabilities re-exposes the handshake snapshot with the live method list.
  • files.list walks the project, skipping node_modules / .git / dist / etc., and filters by glob.
  • files.read returns utf8 content with byte length and truncation flag.
  • Path traversal outside the project root is rejected for both files.read and files.write (10200 InvalidArgument).
  • Reading a nonexistent file returns 10100 NotFound.
  • files.write + files.read round-trips a scratch file (with createDirs).
  • Browser engine and version come back through capabilities (Lightpanda 1.0.0-nightly).
  • session.create opens a browser session with an optional initial URL.
  • session.list includes the newly-created session.
  • browser.eval returns document.title as a value-typed result.
  • browser.dom({mode:"text"}) returns the page's text content.
  • browser.click dispatches a real click — verified by re-querying the mutated DOM.
  • browser.fill dispatches input + change events — verified by re-querying the handler's output.
  • browser.console replays captured console entries (subscribed via Runtime.consoleAPICalled).
  • Missing selector on browser.click returns 10100 NotFound.
  • session.close tears the session down (and CDP Target.closeTarget behind it).
  • Calls before handshake return -32001 HandshakeRequired (covered by dispatcher tests, not asserted at the wire yet).

And there's now a captured walkthrough in section 09 showing the new pi-webdev CLI running against a fixture React project, with the orchestration server correctly detecting React 19 + Vite 7 + Vitest 3 + TypeScript 5 from one package.json read — plus the browser session flow against a tiny counter page.

Measured RTT on a localhost connection: ~0.5ms per ping. That's ~100× under the sub-50ms target in section 01, which means the transport is nowhere near being the bottleneck. The bottleneck will be subsystems — and the in-process files subsystem confirms this: it adds files.read latency that's bounded by Node's fs.readFile rather than the protocol.

0.2What's built

The repo now contains a pnpm workspace with three packages, matching the layout sketched in section 07 Week 1:

PackageWhat's in it
@pi-webdev/shared-types WDP wire types (WdpCommand, WdpResponse, WdpEvent), capability shapes, error codes (WdpError), event method constants. Source of truth for the protocol.
@pi-webdev/server HTTP/WebSocket transport, dispatcher with pre-initialize allow-list, subsystem registry (lifecycle + heartbeat), in-process files subsystem (read/list/write, glob, traversal-guarded), subprocess browser subsystem (Lightpanda + tiny CDP client; navigate / dom / eval / click / fill / console), session lifecycle (create / list / close), session.capabilities, session.subsystems, and the pi-webdev-server daemon CLI.
@pi-webdev/coding-agent Thin WdpClient (uses Node 22's built-in WebSocket), a Pi-extension stub (no hard Pi dependency yet), and the wdp.ping / wdp.filesRead / wdp.filesList tools wired to the corresponding WDP methods.
@pi-webdev/cli pi-webdev binary. --auto boots an ephemeral in-process server; otherwise connects to --url. Subcommands: ping, caps, subsystems, methods, files list|read|write, serve. --json for machine-readable output. Used to capture the demo walkthrough in section 09.

How to run it

0.3What was learned

Things that shifted, sharpened, or surprised across the first two iterations:

An in-process subsystem is a useful subsystem. The plan in section 05 implicitly treats subsystems as subprocesses (Lightpanda, tsserver, Vite). But for a file watcher / file reader, there's no upside to a subprocess — the orchestration server is already Node, and Node's fs.readFile is fast and well-behaved. The subsystem registry shape works for both flavors; the contract is just start / stop / heartbeat. We'll keep the door open for promoting FilesSubsystem to a subprocess if memory or CPU pressure ever justifies it.

Path-traversal guarding belongs in the subsystem, not the dispatcher. First instinct was to centralise sandboxing in the transport layer. Wrong layer — only the subsystem knows what its "valid" addressable surface looks like. files.* guards against escaping the project root; a future browser.* will need entirely different argument validation. Each subsystem owns its security boundary; the dispatcher just routes.

Glob matching is the smallest meaningful filter. Doc 03 §3.2 sketches files.list({ glob }). A 30-line glob→regex translation (supports **, *, ?, [...]) is plenty for v0; chokidar in week 3 will bring proper matching for free.

Static-only capability detection is the right starting point. The plan in section 03 §3.5 mixes static facts (framework, version) with subsystem-live facts (is the dev server up, what's its HMR state). The skeleton draws a clean line: detectCapabilities() only inspects package.json and notable files. Live readiness flows out separately as $/subsystem.status events. This keeps the handshake response stable and cheap — the LLM gets a complete capability snapshot in one round trip, and live state changes are deltas.

The initialized flag wants to live on the connection, not in the dispatcher. First pass tried to maintain an "initialized connections" set on the server and mutate the dispatcher context from outside; it was a tangle. Final shape: each WdpConnection owns a boolean; the dispatcher gets a markInitialized callback in its HandlerContext; the handshake handler calls it. Easier to reason about, easier to test, and the HandlerContext becomes the obvious place for per-connection capabilities like emit too.

Node 22's built-in WebSocket lets the client package stay dependency-free. The server still needs ws for the server-side socket (no stdlib equivalent), but the extension package has no runtime dependencies beyond @pi-webdev/shared-types. That keeps the install surface small for users who only want the Pi extension.

The pre-initialize allow-list is worth being explicit about. $/initialize obviously needs to be callable before initialize. $/ping needs it too — liveness probes shouldn't have to handshake first. Everything else requires the handshake to have completed. The dispatcher's preInitMethods set names this rule instead of leaving it implicit.

Roughly 1,500 LOC of TypeScript across the three packages got the foundation green plus the first subsystem. The smoke test is the spec for now — when we add real subsystems, that file is what proves nothing regressed at the transport/handshake layer.

0.4Where the plan shifted

Small revisions back into the planning docs as we went:

  • Error code allocation. The plan said "-32xxx protocol / 1xxx tool / 2xxx transient" in section 03 §3.7. Implemented the actual codes in shared-types/errors.ts — HandshakeRequired, UnsupportedProtocolVersion, AlreadyInitialized live in -32001..-32003; NotFound got 10100, InvalidArgument got 10200, leaving room for category-by-thousand expansion under the tool-error umbrella.
  • Subsystem registry contract. Doc 05 sketches "spawn, heartbeat, restart" supervision. The skeleton implements all three but ships with restart disabled — we'll tune restart policy (max attempts, backoff curve, crash-loop detection) once a real subprocess subsystem is actually crashing. Premature tuning would be guesswork.
  • Capability advertisement is method-aware. Beyond what doc 03 §3.5 shows, the capabilities.methods array now lists exactly which WDP methods the server will dispatch this session. Pi's extension can use it directly to decide which tools to register — no separate "is this method available" probe needed.
  • Subsystems can be in-process. Doc 05 implies subsystems are subprocesses. The files subsystem is in-process and the registry contract didn't need any changes to support it. We'll add a subprocess-specific sub-interface only when the first real subprocess subsystem (browser, LSP) actually needs one.
  • Sandboxing is per-subsystem. The dispatcher doesn't validate file paths — only the files subsystem does. Each subsystem will own its own security boundary; the dispatcher just routes.

0.5Open from week 1

The dispatcher only enforces "must be initialized" for non-handshake methods, but doesn't enforce anything about which client a method is exposed to. Once we have multi-client sessions (Pi + a TUI dashboard, say), per-client subscriptions and per-client tool surfaces will need a model. Not blocking yet, but worth thinking about before subsystems land.

The Pi extension currently builds against a stub PiExtensionHost interface instead of importing defineExtension from Pi itself. We need to pin a Pi version and replace the stub. Doing this before reading Pi's source carefully (per roadmap §7.8 step 1) would be premature.

Heartbeat runs in-process and trusts the subsystem to return true. Once subsystems are subprocesses, heartbeat needs to span process boundaries — probably a periodic $/ping on the internal stdio channel, with crash detection on EPIPE. That's a week-2 problem.

0.7Week 2 — browser subsystem (Lightpanda)

Lightpanda 1.0.0-nightly is now wrapped as the first subprocess subsystem. The orchestration server spawns lightpanda serve on an ephemeral port, attaches via CDP Target.createTarget + Target.attachToTarget(flatten:true), and exposes the five core browser methods (navigate / dom / eval / click / fill) plus browser.console and the session lifecycle (session.create / list / close).

Full transcript and the captured CLI walkthrough live in demo §9.8. End-to-end Pi-session-style flow (open → eval → click → re-eval verifies state changed) works against a long-running daemon.

What was learned

CDP's flatten mode is the right shape. Older CDP had two modes — browser-level connection plus per-target WebSockets — which is a hassle to multiplex. Target.attachToTarget({flatten: true}) returns a session id that you stamp onto every subsequent message; one socket carries everything. The tiny in-tree CdpClient is ~140 lines and didn't need any other CDP plumbing.

Lightpanda has no layout, and we should be honest about it. document.body.innerText returns text without spacing — "smoke" + "click" comes back as "smokeclick". For LLM use cases that's fine (the model can infer structure from the HTML), but it means we shouldn't pretend the browser surface gives you rendered text. browser.dom({ mode: "text" }) documents this. mode: "html" returns outerHTML when the LLM wants the real source.

Subsystem availability is dynamic but advertised statically. If Lightpanda isn't in PATH, the server skips browser registration entirely — no browser.* methods in the dispatcher, no browser row in session.subsystems, and capabilities.browser.engine stays "none". The LLM never sees half-broken state. When Lightpanda is present, capability fields fill in (engine, version, features, limitations) and the subsystem joins the registry's lifecycle.

The registry's subprocess flow worked first time. The supervision skeleton from week 1 (status transitions, broadcast events on state change) needed no changes to handle a real subprocess. heartbeat() returns this.child !== null && this.cdp.isOpen(); the registry handles the rest. Restart-with-backoff is still off, deliberately — no real crash data to tune it against yet.

What's still in §0.5 open questions

The three uncertainties from §0.5 stand. The Pi extension is still building against a stub host. Heartbeat across process boundaries works for "is the child alive" but not "is the child making progress" — fine for now, will need a real liveness probe (probably a periodic CDP Browser.getVersion) before we run untrusted pages.

0.9Week 3 — file watcher + Vite adapter

Chokidar now watches the project root and emits coalesced files.changed events to every open WDP connection. A 1000-event ring buffer backs files.changedSince(since) so digest construction can pull deltas without a separate subscription. esbuild's metafile drives files.depGraph(entry) — externals are marked rather than resolved, so the graph stops cleanly at node_modules boundaries. The Vite adapter registers as its own subsystem (vite); it stays in disconnected until build.connect({url}) wires it to a real dev server's HMR WebSocket.

What was learned

Watcher ignore rules should be narrower than the lister's. First pass copied files.list's "skip every dotfile" rule into chokidar and immediately broke the smoke test (the test writes under .smoke-tmp/). On reflection: files.list hides dotfiles to keep listings useful for navigation, but the LLM does want to know when .env changes. Watcher now only skips the heavy directories (node_modules, dist, .git, …). Same intent, different defaults.

esbuild with externals marked is the right dep-graph primitive. A full bundle is overkill — we don't need the output, just the metafile. Marking everything that isn't a relative path as external means esbuild stops at the node_modules boundary, the metafile still records the edge, and the call returns in milliseconds for typical entry files. files.depGraph on the smoke test's two-file fixture returned 2 nodes / 1 edge in <50ms.

The Vite adapter is honest about not pretending to be Vite. The plan briefly considered exposing all the Vite plugin-API events as first-class WDP events. The implementation does the smaller thing: subscribe to the HMR WebSocket, translate update / full-reload / error into WDP hmr.update + build.completed / build.failed, and let the rest stay Vite-internal. If Next.js adds an adapter later it emits the same WDP events from its own internal hooks.

HMR ↔ browser is straightforward when there's no layout. Lightpanda has no incremental rendering, so a "soft HMR update" doesn't really exist for our browser. The bridge just calls location.reload() on every open session when the adapter receives a non-accepted update. Cheap, correct, no edge cases.

0.11Week 4 — digest + per-turn injection

DigestService now subscribes to broadcast() — every event the server fans out also goes into a 2000-entry ring buffer. env.digestSinceLastTurn renders a per-connection digest with three layers: machine-readable summary rows (one per domain), raw events list, and a text rendering with the doc-03-style header ("ENVIRONMENT EVENTS since last turn (Xs):"). Budget is chars/4; default 800 tokens. The Pi extension's onTurnStart hook calls the digest and appends as a system message when non-empty.

What was learned

The digest needs to be lazy about cursors. First sketch made the client send since on every call; in practice clients drift, lose state, and the server is the only one that reliably knows when "last turn" was. The implementation maintains a per-connection cursor server-side that auto-advances when no since is provided. Connections that drop forget their cursor on close.

Char-budget over token-budget is fine for v0. Real tokenization belongs in the LLM client, not in the orchestration server (different models tokenise differently). The chars/4 heuristic systematically over-counts but never under-counts, so the digest stays inside any plausible token budget the caller wanted.

Summary rows are more valuable than the raw events list. A naïve "dump every event as JSON" is precisely the failure mode doc 01 §1.3 worried about. The summariser collapses N files.changed into one "files: N changed (top 3 paths)" row, N hmr.update into "hmr: N updates", and only surfaces subsystem state changes when they're crashed or stopped. The LLM gets actionable information first.

0.12Week 5 — TypeScript LSP

tsserver is now spawned as the second subprocess subsystem. types.diagnostics drives geterr async and merges syntactic + semantic + suggestion diagnostics per file by source. types.hoverInfo / definition / references use the equivalent tsserver commands. Diagnostic deltas broadcast as types.diagnostics_changed, recorded by the digest service for the next turn.

What was learned

tsserver's JSON-line protocol is pragmatic enough. Full LSP has Content-Length headers, capabilities negotiation, position-encoding fields, and a long tail of optional features. tsserver's protocol is JSON-per-line, sequence-numbered requests, with five or six event kinds we care about. A ~250-line client handles everything we need; we'd have spent at least double that on full LSP.

Inferred-project mode covers v0. Doc 05 §5.2 talks about per-tsconfig tsserver isolation. Real-world projects increasingly have one tsconfig at the root and rely on path mapping; the multi-tsconfig case is a real but bounded population. v0 uses --useSingleInferredProject and shares one tsserver across the project. Per-project isolation lands when a real user hits the corner.

Async diagnostics need event-driven completion. First sketch awaited geterr's response — but tsserver returns the response immediately with no body, then streams the actual diagnostics as events, then emits requestCompleted. The client now keeps a small map of "geterr in flight" promises that resolve on the completion event, with a 5s safety timeout.

0.13Week 6 — test runner + lint

Vitest and ESLint are now in-process subsystems, auto-registered when the package is present in the project's node_modules. test.run({files?}) runs the named test files (or globs) via Vitest's startVitest("test", filters, {run:true}); test.list uses globTestSpecifications. lint.diagnostics({files?}) calls ESLint.lintFiles(targets). Both broadcast events on completion so the digest can show "tests: 1 changed (UserList.test — was passing, now failing)" deltas.

What was learned

Vitest's Node API is the right boundary. Earlier sketches considered spawning vitest run as a subprocess and parsing its stdout — fragile and slow. The Node API gives structured access to tasks, results, and errors, which is exactly what the LLM needs: structured failures with file paths and messages, not parsed test runner output. Same logic applies to ESLint: ESLint.lintFiles returns structured results.

"Affected tests" is a thin wrapper around files.depGraph. The Pi extension can call files.depGraph({entry: changedFile}), walk the reverse edges, find tests that import the changed module, and pass that list as test.run({files}). We don't need a special "affected" mode in the test runner subsystem itself; the dep graph is the primitive.
