Progress

A living log of what's been built against the plan, what was learned along the way, and where the plan has shifted as a result. The other docs are the destination; this one is the trail.

0.1Where we are

Phase 1, Week 1 is in — foundation skeleton plus the first real subsystem. A Node process boots the orchestration server, a client speaks WDP over WebSocket, handshakes via $/initialize, queries capabilities, lists project files, reads files, inspects subsystem state, and round-trips $/ping.

The smoke test (pnpm smoke) now asserts twelve things end-to-end:

  • Handshake completes with a capabilities snapshot.
  • $/ping echo round-trips; bare $/ping also works.
  • Double $/initialize on one connection is rejected (-32003 AlreadyInitialized).
  • Unknown methods return -32601 MethodNotFound.
  • session.subsystems reports the files subsystem in ready state.
  • session.capabilities re-exposes the handshake snapshot with the live method list.
  • files.list walks the project, skipping node_modules / .git / dist / etc., and filters by glob.
  • files.read returns utf8 content with byte length and truncation flag.
  • Path traversal outside the project root is rejected (10200 InvalidArgument).
  • Reading a nonexistent file returns 10100 NotFound.
  • Calls before handshake return -32001 HandshakeRequired (covered by dispatcher tests, not asserted at the wire yet).

Measured RTT on a localhost connection: ~0.5ms per ping. That's ~100× under the sub-50ms target in section 01, which means the transport is nowhere near being the bottleneck. The bottleneck will be subsystems — and the in-process files subsystem confirms this: it adds files.read latency that's bounded by Node's fs.readFile rather than the protocol.

0.2What's built

The repo now contains a pnpm workspace with three packages, matching the layout sketched in section 07 Week 1:

PackageWhat's in it
@pi-webdev/shared-types WDP wire types (WdpCommand, WdpResponse, WdpEvent), capability shapes, error codes (WdpError), event method constants. Source of truth for the protocol.
@pi-webdev/server HTTP/WebSocket transport, dispatcher with pre-initialize allow-list, subsystem registry (lifecycle + heartbeat), static capability detection, in-process files subsystem (read + list with glob, path-traversal guard, ignore list), $/initialize, $/ping, session.capabilities, session.subsystems, files.read, files.list handlers, pi-webdev-server CLI entrypoint.
@pi-webdev/coding-agent Thin WdpClient (uses Node 22's built-in WebSocket), a Pi-extension stub (no hard Pi dependency yet), and the wdp.ping / wdp.filesRead / wdp.filesList tools wired to the corresponding WDP methods.

0.3What was learned

Things that shifted, sharpened, or surprised across the first two iterations:

An in-process subsystem is a useful subsystem. The plan in section 05 implicitly treats subsystems as subprocesses (Lightpanda, tsserver, Vite). But for a file watcher / file reader, there's no upside to a subprocess — the orchestration server is already Node, and Node's fs.readFile is fast and well-behaved. The subsystem registry shape works for both flavors; the contract is just start / stop / heartbeat. We'll keep the door open for promoting FilesSubsystem to a subprocess if memory or CPU pressure ever justifies it.

Path-traversal guarding belongs in the subsystem, not the dispatcher. First instinct was to centralise sandboxing in the transport layer. Wrong layer — only the subsystem knows what its "valid" addressable surface looks like. files.* guards against escaping the project root; a future browser.* will need entirely different argument validation. Each subsystem owns its security boundary; the dispatcher just routes.

Glob matching is the smallest meaningful filter. Doc 03 §3.2 sketches files.list({ glob }). A 30-line glob→regex translation (supports **, *, ?, [...]) is plenty for v0; chokidar in week 3 will bring proper matching for free.

Static-only capability detection is the right starting point. The plan in section 03 §3.5 mixes static facts (framework, version) with subsystem-live facts (is the dev server up, what's its HMR state). The skeleton draws a clean line: detectCapabilities() only inspects package.json and notable files. Live readiness flows out separately as $/subsystem.status events. This keeps the handshake response stable and cheap — the LLM gets a complete capability snapshot in one round trip, and live state changes are deltas.

The initialized flag wants to live on the connection, not in the dispatcher. First pass tried to maintain an "initialized connections" set on the server and mutate the dispatcher context from outside; it was a tangle. Final shape: each WdpConnection owns a boolean; the dispatcher gets a markInitialized callback in its HandlerContext; the handshake handler calls it. Easier to reason about, easier to test, and the HandlerContext becomes the obvious place for per-connection capabilities like emit too.

Node 22's built-in WebSocket lets the client package stay dependency-free. The server still needs ws for the server-side socket (no stdlib equivalent), but the extension package has no runtime dependencies beyond @pi-webdev/shared-types. That keeps the install surface small for users who only want the Pi extension.

The pre-initialize allow-list is worth being explicit about. $/initialize obviously needs to be callable before initialize. $/ping needs it too — liveness probes shouldn't have to handshake first. Everything else requires the handshake to have completed. The dispatcher's preInitMethods set names this rule instead of leaving it implicit.

Roughly 1,500 LOC of TypeScript across the three packages got the foundation green plus the first subsystem. The smoke test is the spec for now — when we add real subsystems, that file is what proves nothing regressed at the transport/handshake layer.

0.4Where the plan shifted

Small revisions back into the planning docs as we went:

  • Error code allocation. The plan said "-32xxx protocol / 1xxx tool / 2xxx transient" in section 03 §3.7. Implemented the actual codes in shared-types/errors.ts — HandshakeRequired, UnsupportedProtocolVersion, AlreadyInitialized live in -32001..-32003; NotFound got 10100, InvalidArgument got 10200, leaving room for category-by-thousand expansion under the tool-error umbrella.
  • Subsystem registry contract. Doc 05 sketches "spawn, heartbeat, restart" supervision. The skeleton implements all three but ships with restart disabled — we'll tune restart policy (max attempts, backoff curve, crash-loop detection) once a real subprocess subsystem is actually crashing. Premature tuning would be guesswork.
  • Capability advertisement is method-aware. Beyond what doc 03 §3.5 shows, the capabilities.methods array now lists exactly which WDP methods the server will dispatch this session. Pi's extension can use it directly to decide which tools to register — no separate "is this method available" probe needed.
  • Subsystems can be in-process. Doc 05 implies subsystems are subprocesses. The files subsystem is in-process and the registry contract didn't need any changes to support it. We'll add a subprocess-specific sub-interface only when the first real subprocess subsystem (browser, LSP) actually needs one.
  • Sandboxing is per-subsystem. The dispatcher doesn't validate file paths — only the files subsystem does. Each subsystem will own its own security boundary; the dispatcher just routes.

0.5Open from week 1

The dispatcher only enforces "must be initialized" for non-handshake methods, but doesn't enforce anything about which client a method is exposed to. Once we have multi-client sessions (Pi + a TUI dashboard, say), per-client subscriptions and per-client tool surfaces will need a model. Not blocking yet, but worth thinking about before subsystems land.

The Pi extension currently builds against a stub PiExtensionHost interface instead of importing defineExtension from Pi itself. We need to pin a Pi version and replace the stub. Doing this before reading Pi's source carefully (per roadmap §7.8 step 1) would be premature.

Heartbeat runs in-process and trusts the subsystem to return true. Once subsystems are subprocesses, heartbeat needs to span process boundaries — probably a periodic $/ping on the internal stdio channel, with crash detection on EPIPE. That's a week-2 problem.

0.6Next iteration

The roadmap's week 2 target is the browser subsystem (Lightpanda integration, browser.navigate / browser.dom / browser.eval). Before touching Lightpanda we need to:

  1. Build a subprocess-flavored subsystem to actually stress the registry's heartbeat + crash + restart paths. The files subsystem proved the in-process flow; the next subsystem needs to prove the subprocess flow. A trivial EchoSubprocess (Node child that responds to $/ping over stdio) is enough.
  2. Pin the internal subsystem protocol (subsystem ↔ orchestration server) — almost certainly JSON-RPC over stdio, with a smaller method surface than WDP. Doc 05 implies it; we'll write it down.
  3. Try Lightpanda against a real React project (roadmap §7.8 step 2). The go/no-go from doc 04 should run on a real artifact, not on hope.

After that, Phase 0's three-browser-tools spike from roadmap §7.0 is essentially free — once the browser subsystem boundary is real, browser.navigate / browser.dom / browser.eval are thin dispatcher entries.
