Progress

A living log of what's been built against the plan, what was learned along the way, and where the plan has shifted as a result. The other docs are the destination; this one is the trail.

0.1Where we are

Phase 1, Week 1 — foundation skeleton — is in. End-to-end round-trip works: a Node process boots the orchestration server, a client speaks WDP over WebSocket, handshakes via $/initialize, calls $/ping, and reads back static capabilities detected from the project's package.json.

The smoke test (pnpm smoke) currently asserts six things end-to-end:

  • Handshake completes with a capabilities snapshot.
  • $/ping echo round-trips.
  • $/ping works without an echo argument.
  • Double $/initialize on one connection is rejected (-32003 AlreadyInitialized).
  • Unknown methods return -32601 MethodNotFound.
  • Calls before handshake return -32001 HandshakeRequired (covered by the dispatcher path, not asserted directly yet).

Measured RTT on a localhost connection: ~0.5ms per ping. That's a hundred times under the sub-50ms target in section 01, which means the transport is nowhere near being the bottleneck. The bottleneck will be subsystems.

0.2What's built

The repo now contains a pnpm workspace with three packages, matching the layout sketched in section 07 Week 1:

PackageWhat's in it
@pi-webdev/shared-types WDP wire types (WdpCommand, WdpResponse, WdpEvent), capability shapes, error codes (WdpError), event method constants. Source of truth for the protocol.
@pi-webdev/server HTTP/WebSocket transport, dispatcher with pre-initialize allow-list, subsystem registry (lifecycle + heartbeat, no real subsystems yet), static capability detection, $/initialize + $/ping handlers, pi-webdev-server CLI entrypoint.
@pi-webdev/coding-agent Thin WdpClient (uses Node 22's built-in WebSocket), a Pi-extension stub (no hard Pi dependency yet), and the wdp.ping tool wired to $/ping.

How to run it

pnpm install
pnpm -r run build
pnpm smoke               # end-to-end round-trip
# or, manual:
node packages/server/dist/bin.js --port 48710 --project-root .

0.3What was learned

Things that shifted, sharpened, or surprised during week 1:

Static-only capability detection is the right starting point. The plan in section 03 §3.5 mixes static facts (framework, version) with subsystem-live facts (is the dev server up, what's its HMR state). The skeleton draws a clean line: detectCapabilities() only inspects package.json and notable files. Live readiness flows out separately as $/subsystem.status events. This keeps the handshake response stable and cheap — the LLM gets a complete capability snapshot in one round trip, and live state changes are deltas.

The initialized flag wants to live on the connection, not in the dispatcher. First pass tried to maintain an "initialized connections" set on the server and mutate the dispatcher context from outside; it was a tangle. Final shape: each WdpConnection owns a boolean; the dispatcher gets a markInitialized callback in its HandlerContext; the handshake handler calls it. Easier to reason about, easier to test, and the HandlerContext becomes the obvious place for per-connection capabilities like emit too.

Node 22's built-in WebSocket lets the client package stay dependency-free. The server still needs ws for the server-side socket (no stdlib equivalent), but the extension package has no runtime dependencies beyond @pi-webdev/shared-types. That keeps the install surface small for users who only want the Pi extension.

The pre-initialize allow-list is worth being explicit about. $/initialize obviously needs to be callable before initialize. $/ping needs it too — liveness probes shouldn't have to handshake first. Everything else requires the handshake to have completed. The dispatcher's preInitMethods set names this rule instead of leaving it implicit.

Roughly 800 LOC of TypeScript across the three packages got the foundation green. The smoke test is the spec for now — when we add real subsystems, that file is what proves nothing regressed at the transport/handshake layer.

0.4Where the plan shifted

Small revisions back into the planning docs as we went:

  • Error code allocation. The plan said "-32xxx protocol / 1xxx tool / 2xxx transient" in section 03 §3.7. Implemented the actual codes in shared-types/errors.ts — HandshakeRequired, UnsupportedProtocolVersion, AlreadyInitialized all needed numbers, and they live in the -32001..-32003 range to stay inside the JSON-RPC server-defined window.
  • Subsystem registry contract. Doc 05 sketches "spawn, heartbeat, restart" supervision. The skeleton implements all three but ships with restart disabled — we'll tune restart policy (max attempts, backoff curve, crash-loop detection) once a real subsystem like the browser is actually crashing. Premature tuning would be guesswork.
  • Capability advertisement is method-aware. Beyond what doc 03 §3.5 shows, the capabilities.methods array now lists exactly which WDP methods the server will dispatch this session. Pi's extension can use it directly to decide which tools to register — no separate "is this method available" probe needed.

0.5Open from week 1

The dispatcher only enforces "must be initialized" for non-handshake methods, but doesn't enforce anything about which client a method is exposed to. Once we have multi-client sessions (Pi + a TUI dashboard, say), per-client subscriptions and per-client tool surfaces will need a model. Not blocking yet, but worth thinking about before subsystems land.

The Pi extension currently builds against a stub PiExtensionHost interface instead of importing defineExtension from Pi itself. We need to pin a Pi version and replace the stub. Doing this before reading Pi's source carefully (per roadmap §7.8 step 1) would be premature.

Heartbeat runs in-process and trusts the subsystem to return true. Once subsystems are subprocesses, heartbeat needs to span process boundaries — probably a periodic $/ping on the internal stdio channel, with crash detection on EPIPE. That's a week-2 problem.

0.6Next iteration

The roadmap's week 2 target is the browser subsystem (Lightpanda integration, browser.navigate / browser.dom / browser.eval). Before touching Lightpanda we need to:

  1. Add a fake subsystem implementation (e.g. EchoSubsystem) that exercises the registry's full lifecycle — start, ready, heartbeat, crash, restart. The supervision code is currently un-stressed; we should stress it with a subsystem we control before strapping one we don't.
  2. Sketch the internal subsystem protocol (subsystem ↔ orchestration server) separately from WDP. Doc 05 implies it exists but doesn't pin a shape. Probably the same JSON-RPC framing we use externally, over stdio, with a smaller method surface.
  3. Actually try Lightpanda against the team's current React project (roadmap §7.8 step 2). The go/no-go from doc 04 should run on a real artifact, not on hope.

Then the Phase 0 spike from roadmap §7.0 becomes essentially free — three browser tools over WDP is straightforward once the browser subsystem boundary is real.
