Section 02 · Pi integration

Pi integration

Pi is the agent harness, not the product. We integrate via a single npm package — a Pi extension that contributes tools, skills, prompt templates, and a per-turn context injector. Everything routes through the orchestration server; Pi just provides the loop.

2.1Why Pi over the alternatives

The current landscape of coding agent harnesses, ordered roughly by maturity:

HarnessStrengthsWhy not it
Claude CodePolished, Anthropic-backed, great defaultsClosed extension surface, hard to customize the tool loop
Cursor / ContinueIDE-integrated, great UXEditor-coupled; we want a headless dev loop, not a GUI
ClineStrong tool-calling primitivesVSCode-coupled; harder to use as a CLI/CI tool
AiderExcellent file editing, matureWorkflow is opinionated; less extensible than Pi
Custom (from scratch)Total controlMonths of work to rebuild what Pi gives you
PiMinimal core, RPC + SDK modes, real extension system, MIT licenseYoung project; small team behind it

Pi's "primitives, not features" philosophy is exactly what you want when you're building a domain-specific agent: it gets out of the way. Most harnesses fight you when you want to inject custom context, override file-write behavior, or add tools that aren't MCP. Pi assumes you'll do those things and provides the hooks.

Pi is young — one primary maintainer (Mario Zechner / Earendil) and a small contributor base. The risk is real and I cover it in risks. The mitigation is that everything we build is independently usable via SDK mode and a stable protocol, so an alternative harness can be wired in if needed.

2.2The four integration surfaces

Pi exposes four surfaces an extension can contribute to. We use all of them:

Tools

Functions the LLM can call. Each tool maps to a WDP method on the orchestration server. Pi handles schema validation, error formatting, and result serialization.

Skills

Capability bundles loaded on-demand. A skill is a folder with a SKILL.md describing when to load it and what tools come along. We ship skills like webdev-react, webdev-vue, webdev-next, webdev-test — each providing framework-specific context and a curated tool subset.

Prompt templates

Markdown files invoked by typing /name. We ship a handful: /fix-types (load type errors, suggest fixes), /add-route (scaffold a new route), /debug-render (introspect component state and diagnose).

Per-turn context injection

An extension hook that runs before every turn. We use it to inject a digest of recent events — build status, type errors that changed since last turn, HMR updates. This is where the "agent feels the dev loop" magic happens.

2.3The extension shape

A single npm package, @pi-webdev/coding-agent, with this layout:

@pi-webdev/coding-agent/
├── package.json
├── pi-extension.ts          # entry point
├── tools/
│   ├── browser.ts
│   ├── files.ts
│   ├── types.ts
│   ├── test.ts
│   └── inspect.ts
├── skills/
│   ├── webdev-react/SKILL.md
│   ├── webdev-vue/SKILL.md
│   ├── webdev-next/SKILL.md
│   └── webdev-test/SKILL.md
├── prompts/
│   ├── fix-types.md
│   ├── add-route.md
│   └── debug-render.md
└── server/
    └── client.ts            # WDP client, talks to orchestration server

Sketch of the entry point:

// pi-extension.ts
import { defineExtension } from "@earendil-works/pi-coding-agent";
import { WdpClient } from "./server/client";
import { browserTools } from "./tools/browser";
import { fileTools } from "./tools/files";
import { typeTools } from "./tools/types";

export default defineExtension({
  name: "pi-webdev",
  version: "0.1.0",

  async setup({ registerTool, registerSkill, onTurnStart }) {
    const wdp = await WdpClient.connect({
      url: process.env.WDP_URL ?? "ws://localhost:48710"
    });

    // Tool registration — each tool routes to WDP
    for (const tool of [...browserTools, ...fileTools, ...typeTools]) {
      registerTool(tool.name, tool.schema, async (args) => {
        return wdp.call(tool.method, args);
      });
    }

    // Per-turn context injection
    onTurnStart(async (ctx) => {
      const digest = await wdp.call("env.digestSinceLastTurn", {
        sinceTimestamp: ctx.lastTurnTimestamp
      });
      if (digest.events.length > 0) {
        ctx.appendSystemMessage(formatDigest(digest));
      }
    });
  }
});

The actual tool implementations are thin — they exist mostly to give Pi an idiomatic surface (good schemas, helpful errors, clear naming). All real work happens in the orchestration server.

2.4Skills as scope

Skills are how we keep the tool surface small per turn. The full extension might register 30 tools, but a React project only needs maybe 12 of them. The skill system handles this — when the LLM types /use webdev-react or when project detection kicks in, only React-relevant tools are exposed.

A skill is a folder with SKILL.md describing trigger conditions and the tool subset:

---
name: webdev-react
description: Use for React projects. Provides component
  introspection (props, state, hooks), JSX-aware browser
  selectors, and React DevTools-compatible queries.
tools:
  - browser.*
  - inspect.componentTree
  - inspect.componentProps
  - inspect.componentState
  - inspect.hookValues
  - test.runVitest
auto-load-when:
  - file-exists: package.json && deps include "react"
---

2.5AGENTS.md per project

Pi auto-loads AGENTS.md from the current directory and ancestors. We exploit this — the orchestration server, on startup, scans the project and writes an AGENTS.md (or contributes to one) with project-specific facts: framework, routing strategy, test runner, lint config, paths convention. The LLM gets this context for free at every turn.

This may interact badly with users who already maintain their own AGENTS.md. Three options to choose between: append to the existing file, write a separate AGENTS.local.md the orchestration server owns, or surface the context dynamically via the per-turn injector instead of writing it to disk. Probably the last one — disk writes feel intrusive.

2.6How a user installs this

From a clean machine with Node installed:

# Install Pi
curl -fsSL https://pi.dev/install.sh | sh

# Install the orchestration server (also npm-distributable)
npm install -g @pi-webdev/server

# In your project directory
pi-webdev init             # writes a config, starts the daemon
pi install @pi-webdev/coding-agent

# Run
pi                         # Pi starts, sees the extension,
                           # connects to the running daemon

The daemon part is important — most users will want it running continuously, not started per session. A LaunchAgent on macOS, a systemd user unit on Linux, a Service on Windows. The init command sets that up.

2.7Escape hatches

Three things we keep deliberately open:

SDK mode. The orchestration server is usable as a TypeScript library too, not just via WDP. Other harnesses (Claude Code via MCP, Aider via plugin, a custom CLI) can embed it directly.

MCP bridge. Pi explicitly skips MCP, but the orchestration server can expose an MCP server for clients that want it. This lets non-Pi agents use the same backend.

Raw WDP. Anyone can write their own client. The protocol is documented (see section 03), open, and stable.

The goal is that no one ever feels locked into Pi. Pi is the most ergonomic on-ramp; the orchestration server is the actual product.
