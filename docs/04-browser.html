Section 04 · Lightweight browser

Lightweight browser

A purpose-built headless browser that skips the rendering pipeline entirely. Boots in well under a second, takes a fraction of the RAM, exposes a CDP-compatible API for migration. The wedge over Playwright + Chromium is iteration speed in the LLM dev loop.

Stock Lightpanda (1.0.0-nightly) is now integrated as the v0 browser subsystem — see demo §9.8 and Progress §0.7. The "use Lightpanda" branch of §4.1 is what landed; the "fork" and "from scratch" branches stay deferred. The narrow CDP surface (Target.attachToTarget(flatten:true) + Page.navigate + Runtime.evaluate) was enough to back all five WDP browser methods plus console capture.

4.1The build-vs-fork-vs-use decision

Three options, with very different cost profiles:

OptionTime to shipMaintenance burdenCompatibility
Build from scratch2+ yearsForeverYou decide what works
Fork Servo + assemble4-6 monthsHeavyServo's; partial
Fork Lightpanda4-8 weeksModerateLightpanda's; growing
Use stock LightpandaDaysLightLightpanda's; incomplete
Wrap headless ChromiumDaysLight, until you want stealthFull

My recommendation: start with stock Lightpanda, wrap it in the WDP browser subsystem boundary, and only fork when you hit a specific limitation that's worth the cost.

"Use Lightpanda" is the right v0 answer. "Fork Lightpanda" might be the right v1 answer. "Build from scratch" is almost certainly never the right answer for this product — the cost is enormous and the differentiation lives in the orchestration layer, not the browser binary.

4.2What Lightpanda actually is

Lightpanda is a headless browser written in Zig, embedding V8, with no layout or paint pipeline. It's explicitly positioned for AI agent and scraping use cases. Open source under Apache 2.0. Claims (their numbers): 9x faster than headless Chrome, 11x less memory.

It's young — first public release in 2024, still finding its production footing. Web compatibility is a long tail. But the architecture is exactly what this product wants.

What Lightpanda includes:

  • HTML parsing (compatible with WHATWG spec)
  • DOM with the standard interfaces
  • V8 for JavaScript execution
  • Networking (HTTP/HTTPS, cookies)
  • A subset of Web APIs (fetch, XHR, localStorage, basic events)
  • CDP-compatible interface for Playwright clients

What Lightpanda skips:

  • Layout engine (no positions, no getBoundingClientRect values that match real Chrome)
  • Paint and compositor
  • GPU stack
  • Media (WebRTC, video, Web Audio)
  • Service workers (partial)
  • Most non-essential Web APIs

4.3What we keep, what we cut, what we add

The orchestration server's browser subsystem boundary lets us shape what's exposed to the LLM, independently of Lightpanda's underlying capabilities.

Keep as-is

DOM access, JS evaluation, network requests, console messages, cookies, localStorage. These are the bread-and-butter operations for LLM agents, and Lightpanda implements them well.

Wrap with semantic helpers

Instead of exposing raw DOM, we expose a semantic tree: text content, ARIA roles, computed visibility, form state, interactive-element annotations. This is 10-50× cheaper than a screenshot or full DOM dump, and more legible to the LLM. The raw DOM remains available as an escape hatch.

Stub gracefully

WebGL, WebRTC, Sensors, Geolocation — these need to not crash when sites probe for them. We return sensible defaults (WebGL unsupported, Geolocation denied, etc.). Sites that critically depend on these will break; we accept that and document it.

Add: hot-reload integration

The single most valuable addition over stock Lightpanda. When Vite's HMR endpoint fires an update, the browser subsystem applies it directly to the running session, without a full reload. This is what makes the dev-loop integration tight. Requires hooking into Vite's HMR client code or replicating its protocol.

Add: framework introspection hooks

Inject the React DevTools backend (or Vue's equivalent) at page load. Expose component tree, props, state via the inspect.* methods. Covered in section 06.

The HMR integration is non-trivial. Vite's HMR client code is JS that runs in the page, but it expects to be in a real browser with full WebSocket and module support. Some of this comes for free from Lightpanda; some doesn't. May need to write a custom HMR client tailored to the lightweight engine.

4.4Performance targets

These are aspirational. Reality may be 2× worse and the product still wins.

MetricHeadless ChromeTarget
Cold start (binary launch to first command)2-5s< 200ms
RAM per browser context (idle)200-500MB< 50MB
Time to navigate + DOM ready500ms-2s< 100ms (localhost)
DOM snapshot to LLM-readable digest~1s + tokens< 20ms
HMR update applied200-500ms via reload< 30ms in-place

The cold-start target depends on V8 initialization, which is the dominant cost in Lightpanda's startup. V8 isolates take ~50ms to initialize from scratch even in optimal conditions. Reusing a warm isolate via snapshot-based startup gets us under 200ms but adds complexity. May need to be a daemon-with-pool model instead of process-per-session.

4.5The escape hatch to real Chrome

Some operations require a real browser. The agent needs to verify visual correctness, take a marketing screenshot, or run an interaction that touches a Lightpanda-unsupported API. For these, we keep Playwright + Chromium as an escape hatch:

// Default: cheap, in-memory, no layout
browser.dom({ sessionId, mode: "semantic" })

// Escape hatch: real Chromium, slow but full-fidelity
browser.screenshot({ sessionId, engine: "chromium", reason: "visual_verify" })

The orchestration server transparently manages a Chromium pool for these escape-hatch operations. The LLM doesn't think about which engine is which; it just expresses intent and gets the right tool for the job.

Expected mix: 95% Lightpanda, 5% Chromium, by call volume. By wall-clock-time, probably 70/30 since Chromium is much slower per call.

4.6The CDP-compatible facade

Lightpanda already exposes a CDP-ish API, which is good — Playwright code mostly works against it. We preserve this in our subsystem boundary so that:

  • Migration from existing Playwright/Puppeteer code is trivial
  • Power users can drop down to raw CDP when they need to
  • Existing browser tools (extensions, devtools-front-end) work

The semantic tree, framework introspection, and HMR integration are additions, not replacements. CDP-via-Lightpanda is the floor, not the ceiling.

4.7When to fork Lightpanda

Stay on stock as long as possible. Fork when one of:

  • A critical API is missing and PR'ing upstream is slower than forking
  • You need a custom build profile (smaller, smaller-er, with V8 snapshots, etc.)
  • HMR integration requires patches that aren't general-interest
  • You want a build flag that strips features more aggressively than upstream allows

If we fork, the working agreement is: contribute back anything general-purpose. The community is small and benefits from shared improvements.

4.8Alternatives if Lightpanda doesn't pan out

Plan B: drop down to Playwright + Chromium with our own perf optimizations. Snapshot-based isolation, browser pool with reuse, aggressive subprocess management. The orchestration server boundary stays the same; only the implementation behind browser.* changes. Performance is worse but compat is full.

Plan C: jsdom + a real HTTP client. No real V8, just jsdom's incomplete DOM running in the same Node process as the orchestration server. Tiny, fast, breaks on anything React-y. Fine for the simplest of cases — Astro static sites, htmx, server-rendered Next pages without hydration.

Plan D: Camoufox / a Firefox-based engine. Heavier, but has the advantage of being a different fingerprint surface from Chromium. Useful if a future stealth requirement emerges.

4.9The full subsystem interface

The browser subsystem exposes this internal API to the orchestration server. WDP's browser.* methods map almost 1:1 to it:

interface BrowserSubsystem {
  createSession(opts: SessionOpts): Promise<SessionId>
  closeSession(id: SessionId): Promise<void>

  navigate(id: SessionId, url: string): Promise<NavResult>
  reload(id: SessionId): Promise<void>

  // Semantic helpers
  semanticTree(id: SessionId, opts?: TreeOpts): Promise<SemanticTree>
  describePage(id: SessionId): Promise<PageSummary>

  // Standard
  dom(id: SessionId, selector?: string): Promise<DomNode[]>
  evaluate(id: SessionId, expr: string): Promise<EvalResult>
  click(id: SessionId, selector: string): Promise<void>
  fill(id: SessionId, selector: string, value: string): Promise<void>

  // Observers (return streams)
  console(id: SessionId): AsyncIterable<ConsoleMessage>
  network(id: SessionId): AsyncIterable<NetworkRequest>
  errors(id: SessionId): AsyncIterable<PageError>

  // HMR integration
  applyHmrUpdate(id: SessionId, update: HmrUpdate): Promise<void>

  // Escape hatch
  screenshot(id: SessionId, opts: ScreenshotOpts): Promise<Buffer>
}
