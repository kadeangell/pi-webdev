Section 06 · Framework introspection

Framework introspection

The novel piece. React, Vue, and Svelte all have internal trees of components with props, state, and hooks. CDP can't see any of it. We expose the component tree as a first-class queryable structure — so the LLM can ask "what props does this Button receive in the current render" without screenshotting.

6.1Why this matters more than anything else in the system

Watch a developer debug a React bug. They open the React DevTools panel, find the component in the tree, look at its props and hooks, and 70% of the time the bug is immediately visible. The DOM is a downstream representation; the component tree is the upstream cause.

LLMs today don't have this. They either get a screenshot (expensive, ambiguous) or a DOM dump (downstream, hard to map back to source). Neither tells them which component is misbehaving and why.

If we ship just one differentiating feature in v0, this should be it. The protocol and the lightweight browser are infrastructure; framework introspection is the capability that makes an agent meaningfully better at React work than Cursor or Claude Code.

6.2How React DevTools actually works

React DevTools is two pieces:

  • Backend — a JS module that runs inside the page, hooks into React via __REACT_DEVTOOLS_GLOBAL_HOOK__, walks the Fiber tree, and exposes operations
  • Frontend — the UI you see in the browser extension. Talks to the backend over window.postMessage or a port

We use only the backend. We inject it at page load (before any user JS runs), connect to it via the browser subsystem, and expose its operations through WDP. The DevTools UI is replaced by the LLM and the orchestration server.

The __REACT_DEVTOOLS_GLOBAL_HOOK__ contract

React itself checks for this global at module init. If present, React calls into it on every commit (when the tree changes). The hook gets:

  • The renderer instance (one per ReactDOM/React Native/etc.)
  • The Fiber tree root
  • Commit events with priority and reason

The backend installs this hook and uses it to maintain a mirror of the Fiber tree, then walks the tree to extract props, state, and hooks on demand.

What we inherit, what we wrap

React DevTools ships its backend as a standalone npm package (react-devtools-core) intended for React Native debugging. We can use this same package directly — connect via WebSocket instead of postMessage, get the same operations.

// Inside the page, injected by the browser subsystem
import { initialize, connectToDevTools } from "react-devtools-core";

initialize();  // installs __REACT_DEVTOOLS_GLOBAL_HOOK__
connectToDevTools({
  host: "localhost",
  port: 48711,
  resolveRNStyle: null
});

On the orchestration server side, we run a tiny WebSocket server on port 48711 that speaks the React DevTools wire protocol. We translate its operations into WDP responses.

The React DevTools wire protocol is internal and not formally documented. It's stable enough that the same client/server pair works across many React versions, but it could change without warning. We may need to track Chrome-extension React DevTools releases and bump compat.

6.3What we expose via WDP

Five primary queries:

inspect.componentTree({ sessionId, depth? })
  → tree of component nodes with names, IDs, parent links

inspect.componentByQuery({ sessionId, query })
  → resolve a query like "Button containing 'Submit'" to component IDs

inspect.props({ sessionId, componentId })
  → props object for that specific component instance

inspect.state({ sessionId, componentId })
  → state values (useState) + reducer state + hook values

inspect.context({ sessionId, componentId })
  → context values that component reads

Stable IDs across renders and HMR

The biggest implementation problem in this domain. React's Fiber objects are not stable — every render produces new ones. The DevTools protocol synthesizes stable IDs from path-in-tree + component name + key, which mostly works but has edge cases when keys change.

For our use case, we need IDs stable enough that the LLM's "the third Button in the list" reference survives:

  • A re-render (Fiber objects replaced)
  • A HMR update (component module replaced)
  • A state change that doesn't structurally reshape the tree

What we do: hash (component-display-name + DOM-position-path + key-if-present) at each commit. Persist these IDs across commits. When the tree restructures significantly, IDs get reassigned and the LLM's references become stale; the digest surfaces a tree_restructured event so the agent knows to re-query.

"DOM-position-path" only works for components that render to the DOM. Components that return null, render Portals, or use Fragments make this trickier. Probably good enough for most cases; will need iteration.

6.4Example LLM workflow

To make the value concrete — what the LLM actually does with these tools:

// User: "The UserList shows undefined names. Fix it."

// LLM step 1: see the tree
tool inspect.componentTree({ sessionId: "main" })
→ { tree: [
    { id: "App.1", name: "App", children: [
      { id: "Layout.1", name: "Layout", children: [
        { id: "UserList.1", name: "UserList", children: [
          { id: "User.1", name: "User" },
          { id: "User.2", name: "User" },
          { id: "User.3", name: "User" }
        ]}
      ]}
    ]}
  ]}

// LLM step 2: look at UserList's props and state
tool inspect.props({ componentId: "UserList.1" })
→ { props: { users: [
    { id: 1, fullName: "Alice" },
    { id: 2, fullName: "Bob" }
  ]}}

tool inspect.props({ componentId: "User.1" })
→ { props: { user: { id: 1, fullName: "Alice" }}}

// LLM step 3: look at the source — User component is reading user.name, not user.fullName
tool files.read({ path: "src/components/User.tsx" })
→ "...<span>{user.name}</span>..."

// LLM step 4: fix
tool files.write({ path: "src/components/User.tsx", content: "...{user.fullName}..." })

// Digest at next turn confirms the HMR update applied and the bug is gone.

Notice: no screenshots, no DOM scraping, no "describe the page" round-trips. The LLM goes directly from "something looks wrong" to "I can see exactly which prop mismatch caused it" in three structured tool calls.

6.5Hook value extraction

The hardest part. useState, useReducer, useEffect, useMemo, useRef, custom hooks — each has a different shape in the Fiber tree's memoizedState linked list.

React DevTools' backend already does this extraction (the "Hooks" panel). The wire protocol exposes hook values keyed by index. Custom hook names are inferred via static analysis or React's useDebugValue.

We expose hook values in two forms:

// Simple — keyed by index
inspect.state({ componentId })
→ { hooks: [
    { kind: "useState", value: "alice" },
    { kind: "useState", value: 0 },
    { kind: "useEffect", deps: [], hasCleanup: true },
    { kind: "useCustom", name: "useUser", value: { id: 1, ... }}
  ]}

// Named — when source-map analysis can resolve the variable name
inspect.stateNamed({ componentId })
→ { username: "alice", count: 0, currentUser: { id: 1, ... } }

The named version is much more useful to an LLM but requires source-map work. Ship the indexed version first; add named extraction in a later phase.

Variable name resolution for hooks involves parsing the component source, matching useState call sites in order, and extracting the destructured names. Doable but tedious; SWC or Babel makes it tractable. Worth doing because it's the difference between "hooks[0] is 'alice'" and "username is 'alice'" in the LLM's eyes.

6.6Vue and Svelte: out of scope for v0, sketched here

Each framework has its own debugging-backend equivalent:

FrameworkBackendTree concept
Reactreact-devtools-coreFiber tree, hooks, context
Vue 3vue-devtools backendComponent tree, refs, reactive state
Sveltesvelte-devtools backendComponent tree, stores
Solidsolid-devtools (separate npm)Owner graph, signals

The pattern is the same — install a backend in the page, expose a tree of components with state. The orchestration server's WDP inspect.* methods stay framework-agnostic; the adapter underneath changes.

For v0, React only. Vue and Svelte are post-MVP; community contribution or paid customer pull will decide order.

6.7Where this breaks

Honest about what won't work:

Production builds with minified component names. If the LLM is debugging a production-built React app, component names become r, i, p. We can still expose the tree, but the LLM can't reason about it semantically. The user's project is dev-mode by default, so this is mostly fine.

Server Components. Next.js RSC, Remix loaders, and Astro server islands all run server-side. The Fiber tree the browser sees is a snapshot, not a live source. We can introspect the rendered output but not the server-side render. Useful but partial.

Compiled-away components. Svelte and Solid compile components to inline code. Their "component tree" is reconstructed by the devtools backend from runtime instrumentation, which means the tree is less rich than React's. Less powerful introspection.

Streaming UI / Suspense boundaries. A component that's still suspending doesn't have a stable tree state. We surface a suspended flag and the LLM should treat it as a special case.

6.8Performance

The tree walk is fast — React DevTools does it in real time in the browser DevTools panel without noticeable lag. Expect <20ms for trees of a few hundred components.

Where it gets slow: serializing large props objects to JSON for transmission over WDP. A component receiving a 50KB array prop will pay for that serialization on every query.

Mitigation: lazy serialization. Tree responses don't include props; props are queried per-component on demand. Large props are summarized (array length, sample of first N items) by default with a verbose flag for full content.

6.9The broader vision

Once component-tree introspection is shipped, several extensions become natural:

  • Time travel. Snapshot the component tree at each commit; let the LLM step back to "what did the tree look like before the bug appeared?"
  • Why-did-you-render. Automatically attribute renders to prop/state/context changes; surface unexpected renders to the LLM
  • Cross-references. "Find all components reading from this Context" or "all components that call this hook"
  • Visual + structural correlation. Map a screenshot region back to the component instance that rendered it (this is what the React DevTools "Inspect" mode does)

All of these are post-MVP, but each one is straightforward once the introspection backbone is in place.
