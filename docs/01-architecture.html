Section 01 · Architecture

Architecture

Five layers, one shared protocol, a strict separation between the LLM brain and the local dev environment. State lives in the orchestration server, not in Pi and not in any subsystem. That's the single most important design decision in the system.

1.1The five layers

From top to bottom:

Layer 1 — LLM

Any frontier model. The orchestration system is model-agnostic by design, because the model choice changes every few months and you don't want the rest of the stack coupled to it. Pi already supports 15+ providers; we inherit that. The LLM's interface to the world is the Pi tool surface.

Layer 2 — Pi (agent harness)

Pi handles the loop primitives: turn-taking, tool calls, message history, context compaction, skill loading. We don't replace any of that. Pi's RPC mode (JSON over stdin/stdout) and SDK mode (embed-as-library) are the two integration surfaces we use.

Layer 3 — Orchestration server

The new piece. A long-running local process that maintains an authoritative model of dev environment state — files, type errors, build status, browser sessions, framework state — and exposes it to Pi via the WebDev Protocol (WDP). All subsystems are children of this process. State changes flow up; commands flow down.

Layer 4 — Subsystems

Independent processes the orchestration server supervises. The lightweight browser, file watcher, TypeScript LSP, dev server adapter, test runner, framework introspection. Each speaks a narrow internal protocol to the orchestration server. None of them talk to Pi directly.

Layer 5 — The user's project

The thing being worked on. The orchestration server treats this as read/write source-of-truth for files but maintains its own indexed view (build status, dep graph, type errors, current browser state) so the LLM doesn't pay re-indexing cost every turn.

1.2Why this shape

Three principles drove the layering:

Single source of truth for state. If both Pi and the orchestration server tried to track build status, they'd drift. The orchestration server owns state; Pi reads it through queries. This is the same reason React has one reducer per concern.

Subsystems are replaceable. Lightpanda might not work out — we should be able to swap in Chromium-via-CDP without changing the protocol. Vite's adapter implementation has nothing to do with Next.js's. The orchestration server provides a stable boundary that absorbs subsystem churn.

Pi is opinionated, but we're not. Pi has decided to skip MCP, sub-agents, and plan mode. Some users will want those things. The orchestration server should be usable from any agent harness — Pi is just the most ergonomic one to start with. The SDK boundary makes that possible.

1.3Dataflow

Two distinct flows, with different latency profiles:

Command flow (LLM → environment)

LLM   →   Pi tool call   →   RPC to orchestration server
                                ↓
                              dispatch to subsystem
                                ↓
                              return typed result
                                ↑
                              event bus updates internal state
                                ↑
                              Pi receives response, continues turn

Latency target: sub-50ms for read operations, sub-200ms for writes that touch the dev server. The orchestration server caches aggressively; reads that hit cache should be sub-5ms.

Event flow (environment → LLM)

subsystem emits event   →   orchestration server
                              ↓
                            event bus, with backpressure
                              ↓
                            buffered until next Pi turn
                              ↓
                            injected into context as system message

Events don't interrupt the LLM mid-turn. They're batched and surfaced at the start of the next turn as a digest, scoped to events that are relevant to recently-edited code. Without this digest, an LLM editing a React component would get a flood of "file changed, build started, build finished, HMR fired, browser updated" events that bury the actual signal.

The event digest format is the single most important design problem in the protocol, and I don't have a final answer. The naive approach (a JSON object dumped into a system message) wastes tokens. A structured summary the LLM can choose to expand needs careful prompt engineering. Worth prototyping three or four formats against real workloads before committing.

1.4Where state lives

StateOwnerLifetime
Conversation historyPiPer session
Project file indexOrchestration serverProcess-long, persists across Pi sessions
Dependency graphOrchestration serverProcess-long
Type errorsSubsystem (LSP)Streamed; orchestration caches latest
Build statusSubsystem (dev server)Streamed; orchestration caches latest
Browser sessionSubsystem (browser)Per browser context
Component tree snapshotSubsystem (framework introspection)Live, queried on-demand
Skills, AGENTS.md contentPiPer session, file-backed

One useful consequence: an orchestration server can be running long before Pi attaches, and can keep running after Pi quits. You can imagine a daemon model where the server is started by your editor or shell login, indexing your project continuously, so when you fire up Pi it has immediate full context.

1.5What CDP does and what it misses

Chrome DevTools Protocol gives you a runtime view of one browser:

  • Page lifecycle (navigate, load, unload)
  • DOM and CSSOM access
  • JS evaluation and console output
  • Network requests in and out of the page
  • Input synthesis (mouse, keyboard)
  • Screenshots and PDF rendering

What it doesn't give you, and what WDP needs to:

  • File system state — what files exist, what changed, what depends on what
  • Type system state — TypeScript errors with positions, hover info, definitions
  • Build state — compilation status, bundling errors, asset graph
  • Dev server state — HMR events, route table, middleware chain
  • Framework state — React component tree with props, hook values, context
  • Test state — pass/fail per test, with diffed output
  • Lint state — diagnostics from ESLint, Prettier, project-specific rules

The point isn't that CDP is bad — it's that CDP solves one narrow problem and we're solving a wider one. Internally, the lightweight browser subsystem speaks something close to CDP for compatibility. The orchestration server's public protocol (WDP) is the superset.

1.6Why a server, not a library

One alternative architecture: ship the orchestration logic as a TypeScript library that Pi loads as an extension. No separate process. Simpler.

Reasons not to:

Long-running indexing. File watching, TypeScript incremental compilation, dependency-graph maintenance — these want to outlive any single agent session. A daemon stays warm; a library reloads cold.

Multiple clients. One orchestration server should be usable by Pi, by your IDE, by a CI test, by an MCP-compatible agent. A library binds you to one host.

Subsystem supervision. The browser, LSP, dev server adapter are subprocesses. Pi shouldn't be in the business of managing those.

Crash isolation. If the LSP crashes, you don't want Pi to crash. Separate process, separate fate.

The cost of this choice is the protocol becomes a real public artifact you have to version and document, instead of "whatever the library API happens to be this week." For a product, that's correct. For a personal tool, it'd be over-engineering.
